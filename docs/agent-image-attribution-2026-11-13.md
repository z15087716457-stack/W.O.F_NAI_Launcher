# Agent 历史图片被误认为本条附件的排查

2026-11-13。用户报告：发送纯文字后，模型突然声称用户又发了一次先前的图片。当前桌面仍为 2.3.3+100；本次最终只补测试与排查记录，无生产代码变更。未安装、启动 Studio、提交 Git、调用真实模型／NAI，或修改 CPA 配置与运行状态。

## 已核实与未确定的部分

- 原始会话 JSONL 中，对应用户消息只有一个 text 块，图片数为 0；模型随后的正文却称用户重复贴了旧图。用户之后的纠正消息同样不含图片。
- 用已安装的 Pi 1.5.0 解析原会话，在那条用户消息处恢复实际分支，并以已安装的 Anthropic 序列化器重建请求。最新用户消息仍为 0 张图；11 张图分布于 5 条较早的用户消息，最早那组两张图留在原来的历史位置。Flutter 当前附件组装、宿主 prompt 与 SDK 逐条序列化路径中未发现把旧图重新附到本条消息的行为。
- 本地重建在 onPayload 截获后主动终止；未向 CPA 或模型发送请求，网络调用数为 0，原 JSONL 字节未变。这是发送边界的复现，不能冒称当时完整 HTTP 请求的抓包。
- 应用序列化结果没有 `pasted_image_1.png`。另一次较早的 CPA 错误追踪显示，该类名称由 CPA 转换上游请求时生成；它在那次记录中也出现在各自的历史／当前消息组。仅凭模型说到这个名字，不能证明本轮发生了串图。
- 没有找到问题发生时那轮成功请求的完整上游载荷，所以尚不能区分模型自身误认与转发之后的上下文转换问题。之前模型自行提出的“provider 把旧图叠到最新消息”仍是猜测，不能写成结论。
- 图片首看高清／历史压缩功能尚未安装到 +100，这次现象不能归因于该待交付改动。

## 处理结论

当前使用的 Pi 1.5.0 依赖消息角色、顺序及各自的图片块区分来源，默认不附加“本条 0 张新图”的说明。本次没有复现客户端把图片移到最新消息，额外软提示不能证明解决了上游误认。

最初加入的零新附件说明已在用户指出复杂度后撤回，`image-context.mjs` 与本次排查前字节一致。最终只保留验证消息归属的测试和排查证据；不改请求提示、聊天记录、用户文字、附件或原图，也不删除历史来掩盖现象。后续如复现，应取得那轮转发后的实际请求，再根据证据修具体故障。
