# 外部快速拖图卡住调查

状态：发现并修复全局拖图入口的两处时序缺陷，仅源码完成，未构建／安装；桌面仍为 **2.3.4+103**。对方具体拖图来源、版本和线程栈未知，不能把隔离测试通过称为已复现并解决所有 Windows「未响应」。

## 已确认的问题

截图仍显示全局「拖拽图片到这里」浮层，且窗口已被系统标记为未响应；该浮层来自 `GlobalDropHandler`，不能据此判断是在松手前还是松手后阻塞。

原入口虽然立即返回原生回调，但后台继续持有 `event.session`，使用 `DroppedFileReader.read` 等待本地 URI、建议名称后才索取图片；多图还要等前一张读取及弹窗处理结束才访问下一张。原生读取启动过晚、会话状态被后续拖放改变时存在问题；同项目的参考图／Agent 拖图入口已有 `capture` 机制，全局入口遗漏了接入。

另一个确定问题是处理中仍返回 `DropOperation.copy`，没有阻止第二次进入 `_handleDrop`。快速重复拖入可同时占用读取来源、处理状态和导入弹窗。

改前隔离复现证据：[日志](../.dart_tool/external-drop-freeze-20261115/reproduce-before.log)。两个测试均失败：回调返回前两张图的读取次数为 `[0, 0]`；首张读取未完成时第二次拖入仍被接受。还观察到组件销毁后继续读取 `ref` 的异常。

Windows 的 Drop 协议包含取得数据、清理反馈和释放数据对象，见 [Microsoft IDropTarget::Drop 文档](https://learn.microsoft.com/en-us/windows/win32/api/oleidl/nf-oleidl-idroptarget-drop)。本地使用的 `super_native_extensions 0.8.24` 在原生 `on_drop` 等待 Dart 回调结束后调用 `drop_end`；只有来源声明异步能力才启用异步数据对象。**因此，旧代码对外部来源生命周期的假设不可靠；这是源码和协议层面的判断，尚不是对方真实冻结线程的诊断。**

## 修正

- 回调内立即捕获所有条目，复用 `DroppedFileReader.capture` 发起读取；后续只等待已取得的 Future，不再访问结束后的会话或读取器。
- 解码、元数据处理与目标选择弹窗仍逐张执行，原生回调不等待导入流程。
- 正在读取剪贴板或处理拖入时拒绝新拖入，避免抢读与重叠弹窗；拖放结束清理高亮。
- 单个读取来源出错不会阻止其他条目开始读取；组件销毁后停止处理，结束时释放忙碌状态。

保留内部历史图片、图库拖放分流、Vibe、本地文件、虚拟图片与网页图片原有格式支持。没有升级 SDK／插件，也没有修改用户草稿、素材或安装目录。
