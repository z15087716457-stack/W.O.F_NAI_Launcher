# 图库 RAG“继续”长时间等待 · 2026-10-17

用户最终澄清操作是暂停后点击“继续”，不是“重建索引”。当前桌面为 r18 / 2.0.0-preview+22。本次只读查代码并运行小型合成诊断，未操作运行实例、打开用户索引、加载真实模型或修改生产代码。

## 已确认的路径

1. 来源未变且原任务仍在时，Worker 直接恢复同一 generator；合成对照确认不重载／保存共享 ANN。见 `tool/rag/worker.py:126`。
2. 暂停期间来源签名改变时，恢复会关闭旧 generator、重新 preview 并创建新任务。图库签名继承整个源 SQLite 与 WAL 的大小／mtime，未限定到图库内容本身；无关数据库编辑也能触发。见 `tool/rag/documents.py:35`、`tool/rag/gallery.py:67`。
3. 关闭已经启动的 build generator 会抛出 `GeneratorExit`，落入 Engine 的 `except BaseException`，回滚后调用 `_load_ann()`；`finally` 再保存整个共享 ANN。若保存的全局 generation 落后，`pool.reload()` 会从全部分区读取向量重建索引。仅更新未变化条目的 `seen` 也会通过触发器推进全局 generation。见 `tool/rag/engine.py:162`、`:198`、`tool/rag/pool.py:31`、`:42`。
4. 新任务从 `processed = 0` 开始逐条核对 digest。相同内容复用向量，但仍执行数据库查询、更新及提交。图片每 8 项、参数每 32 项产生一次进度；每次进度经过自身及 Gallery 聚合状态，合计执行 3 次 `SUM(length(vector)+length(text)+length(name))` 分区汇总。图库规模较大时累计扫描昂贵。见 `tool/rag/engine.py:112`、`:152`、`:184`、`tool/rag/gallery.py:203`、`:225`。
5. 设置页图库数字显示 `visual_indexed`／`parameters_indexed`，没有展示重新校验的 `processed`。因此核对旧条目时计数可以始终不动；用户看到的“还没开始”可能包含了后台校验。见 `lib/presentation/wiring/settings/settings_rag.dart:98`。

Worker 使用单个执行线程，建库任务按批次入队；截图中的标签建库与图库共用该线程及模型。命令优先级只在批次间生效，不能中断正在执行的推理、全池重载或保存。这会增加等待，但本次没有测量现场各阶段耗时，不把十分钟全部归因于排队或模型加载。

## 合成验证

诊断位于 `.dart_tool/rag-resume-audit-20261017/probe.py`，结果 `result.json`。复用现有 GalleryTests 的临时数据库、微型 PNG 和 FakeModels，约一秒完成，不模拟用户真实规模的时间。

- 131 张已入库图片、130 段已入库参数，再核对产生 22 次进度事件、66 次完整分区大小统计；新增图片与文本向量均为 0，全部事件的入库计数保持不变。
- 来源未变化的直接恢复：全池重载 0 次、保存 0 次。
- 仅新增一张无关表后点击继续：来源签名变化；此前未变条目的更新已使 ANN 检查点过期；恢复命令内发生全池重载 1 次、保存 1 次。

这些结果确认恢复流程存在重复工作，不能据此给出用户现场十分钟的分阶段占比。已有向量会复用，问题集中在恢复／失效判定、全池索引维护和进度统计。

## 待修方向

精确到来源内容的变更判定；预期暂停／取消不进入异常全池恢复；检查点只在必要时保存；状态大小增量维护；恢复按变化项及断点继续，并展示检查／载入／编码阶段。共享向量池、来源过滤、原图及已有索引的保护继续保留。尚未实施、构建或安装修复。
