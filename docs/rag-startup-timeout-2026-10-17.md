# RAG 启动超时与“未建库”误报 · 2026-10-17

用户确认发生在刚启动 Studio，有时先看到全部“未建库”，随后全部 timeout。本次只读代码、进程／Windows 事件及索引元数据，未操作运行实例、请求模型、载入 ANN、重建或清除索引，也未修改生产代码。

## 本机证据

现有共享池约 3.14 GB，ANN 文件约 2.37 GB。只读 SQL 计数：标签 638024、块 727、图库画面 19488、参数 77920，合计 **736159**；保存的 ANN 计数也是 736159。数据库 generation=1284414，ANN 保存的 generation=1260726，版本不一致。数量一致不代表逐条内容已作完整校验，但明确不是截图中的“全部 0”。证据 `.dart_tool/rag-timeout-audit-20261017/result.json`。

`VectorPool.reload()` 在 generation 不一致时放弃已有 ANN 检查点，读取所有已存向量重新构建检索索引。这里复用向量，不是重新跑全部 Embedding。SQLite 对任意行 UPDATE 都增加 generation，更新 seen 也会失效；此次版本差由哪些写入产生没有历史日志，不能全部归于 seen。代码见 `tool/rag/pool.py:31`、`:42`。

## 启动链路问题

- `RagController._open()` 的 configure 使用 RagClient 默认 **60 秒**超时。Worker configure 先构造 VectorPool，完整载入／重整索引后才返回所有来源状态。若超过期限，客户端发取消并关闭工作进程；refresh 把错误写到全部启用来源。
- 现有状态心跳也限时 60 秒，且仅豁免“有搜索请求在途”的超时。建库批次／初始化阻塞是另一条仍可触发整体错误的路径。本次触发场景与 configure 更吻合；未找到当时应用日志，不能声称已直接记录到超时的 operation 或实测重载耗时。
- 初始 RagStatus 计数为 0；即使 controller 已切到 loading，`settingsRagData()` 没有单独展示 loading，最终落到 empty，显示“未建库”及建立按钮。头部就绪来源于独立的解释器／依赖探测，不等于索引已读取，因而能同时出现“已就绪／未建库／0%”。

因此最符合现有证据的链路为：启动 → 检查点过期 → 重整约 73.6 万条向量 → 尚未返回状态时误显示未建库 → 60 秒初始化截止 → 四个来源一起 timeout。已确认代码和本机数据满足此路径条件，实际耗时及具体超时请求仍缺当时日志。

## 修正方向（未实施）

启动先读取轻量来源摘要并展示“正在读取索引”；状态未知时不显示空库或重建入口。将共享池初始化／恢复与普通短请求区分，展示真实准备状态和进展，避免固定 60 秒误杀正常恢复；仍需保留取消与无进展保护。进一步让 generation 只因影响检索的字段变化而失效，避免仅状态更新触发全池重整；正常退出可靠保存检查点。原生 APPCRASH 另取调用栈定位，不根据系统模块名直接更改渲染或模型设置。
