## 已复现的原因

按当前生效词库读取，638,963 个标签对应 1,004,466 条视图记录，已保存位置与截图一致。直接取接下来待处理的 32 条，在当前本地 Gemma 2、CUDA 和原代码上复现：

`ImportError: To load a video from YouTube url you have to install yt_dlp first.`

Sentence Transformers 的多模态输入格式化器会猜测裸字符串的类型。百科文字中的 YouTube 链接被路由到视频处理器，随后缺少视频下载依赖而失败；仅关闭模型配置中的音频和视觉组件不能替代明确输入类型。这是文本路由错误，不是旧索引损坏。

另有两个已核实的问题：

- 普通来源错误后的「重试」直接调用 `onRagRebuild`，因此出现会清空当前来源的重建确认。
- 工作进程只在错误事件中报告失败，随后的状态刷新又把来源当作普通未完成任务；自动更新会重新启动，反复核对已有前缀。现场向量数量不动而来源批次计数持续增长，与这一行为一致。已消失的任务句柄原先还能返回成功，使客户端误以为正在继续。

当次超时的具体排队阶段缺少原始日志，结论以实际失败批次和重试路由的复现为准。

## 修复后的行为

- `Models.embed` 把每条文字明确传为 `{'text': text}`，文档和查询均保持原提示模板。链接、文件名、路径都作为文字编码，图库图片继续使用既有图片入口。
- 失败原因以脱敏错误码写入来源 `build_error` 元数据，心跳及重启后仍可见，自动更新不再反复重跑失败任务。用户明确开始续建时清除错误，已提交向量按 digest 跳过。图库画面与参数两路、旧标签清理重试一起覆盖。
- 「重试」复用普通建库计划，不传重建标志；未变向量直接复用。更多菜单中的显式重建仍有原来的危险操作确认。
- 恢复请求遇到失效句柄时，工作进程返回 `job_missing`；客户端创建新的续建任务，不把不存在的任务标成一直忙。其他错误继续沿原失败路径报告。
