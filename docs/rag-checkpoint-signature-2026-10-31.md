# 标签来源签名与 WAL checkpoint

状态：2026-10-31 已随 **2.2.2+70** 安装，与 Skill 精简一并交付。[本机安装与回退](local-2.2.2-build70-2026-10-31.md)。

## 原因与修复

此前来源签名使用主库与非空 WAL 的大小、修改时间。最后一个写连接关闭或执行 checkpoint 时，已提交页面从 WAL 合并回主库；资料未变，物理文件签名却变，刚完成的标签索引因此又成为 partial。+69 的空 WAL 修复没有覆盖这个情况。

现在使用 SQLite 只读事务可见快照的内容摘要作为标签基础来源身份，已提交 WAL 页面由 SQLite 自身合并读取。物理文件信息仅作摘要缓存键；缓存最多 32 个摘要字符串，连接及临时映像计算后释放。文件未变化时直接复用摘要，查询与批次检查无需反复读取整库。使用标准 [Python sqlite3 Connection.serialize](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.serialize)，未新增依赖。

完成记录中的 `complete_signature`、`source_base` 与 `semantic_revision` 统一使用本次计划实际校验过的来源状态。结束时不重新认领一个未经本次扫描验证的新版本，保留最后一刻真实修改的待同步状态。`source_state` 只在内部计划保存，不增加前端协议字段。

索引、向量格式、资料 digest、召回与排序保持。既有补充库锁定降级保持。旧物理签名首次升级为新签名时仍需对齐核对一次，资料 digest 未变则复用原向量；之后已覆盖的 checkpoint／连接关闭不再引发重复核对。这里不把 VACUUM、文件替换等所有维护操作承诺为签名不变。
