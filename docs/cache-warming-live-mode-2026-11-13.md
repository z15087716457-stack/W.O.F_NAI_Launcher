# 缓存保温运行中切换

2026-11-13：修正运行中开启保温只改模式、未接续当前请求的漏项。仅源码交付，桌面仍为2.3.3+100；未启动Studio、安装、提交Git或调用真实模型／NAI接口。

## 原因与行为

设置会通过Dart、宿主`settings`到达Pi，漏项在固定Pi1.5.0的`setCacheWarmingMode`：它只协调已有CacheWarmer任务。原请求开始时处于`off`会直接跳过保温，运行中再启用没有任务可协调。修复前本地宿主复现：期望`scheduled`，实际`inactive`。旧界面还将所有非活动状态统称「待机，下次运行时开始」，无法仅从截图区分关闭后热开启、错过续期窗口或其他停止原因。

现在运行中启用会接续当前仍有效的请求前缀，不重跑聊天任务。首次续期按原请求时间计算；曾成功保温后关闭再开启，按最后实际续期计算。已有保温任务切换运行／空闲模式保持原倒计时。过了续期窗口不重放，当前上下文不匹配或SDK不允许重放时不启动；本轮已经结束后切模式不会唤醒旧请求。保温仍在原计划时机用一Token续期，启用不等于立刻发一次保温请求。

界面用五语言区分续期时机已过、上下文已变、时长上限、当前请求不支持及预计收益不足；关闭、正常待机与续期倒计时保持原有显示。

## 兼容边界

补丁集中在`tool/nai_agent/lib/extensions/cache-warming.mjs`。Pi1.5.0未提供公开的恢复当前请求接口，兼容层使用固定版本的`session._cacheWarmer`，记录其原`start`调用和`isCurrent`校验，补接首次计时器；后续刷新、取消和30分钟／1小时安全限额继续走原SDK。保留原开始时间、原TTL／延迟／截止窗口，以及原请求安全重放检查。未修改`node_modules`或升级依赖。

升级Pi时须重新检查该内部接口并运行本报告中的热切换／过期回归；不要把兼容层静默套到未知SDK。未知计费仍不伪造缓存收益，已知计费继续采用Pi判断。
