# 桌面退出流程优化

本项已随 [2.2.4+78](local-2.2.4-build78-2026-11-02.md) 本机安装完成。下文保留源码完成时的验证记录。

日期：2026-11-02。源码完成，**尚未安装、制作分发包或推 Git**；桌面仍为 2.2.4+77。改动前的证据见[退出调查](app-exit-investigation-2026-11-02.md)。

## 行为与实现

- 继续使用 `DesktopAppShutdownService`：明确退出先隐藏主窗口，独立后台 cleanup 同时开始取消并等待收尾，全部结束后依次关闭数据库、Hive、托盘，flush 日志后调用一次 `exit(code)`。
- 移除原来的 `windowManager.destroy()` 和 `setPreventClose(false)`，不再提前结束原生消息循环、拆 Flutter 引擎后又期待 Dart 继续执行退出。已有退出 Future 继续合并重复请求。
- 普通窗口关闭仍是隐藏到托盘，只把 hide 前移，不等待资源小窗的清理；小窗关闭动作保留。退出期间托盘恢复、右键菜单、唤醒以及窗口状态事件不再恢复窗口或补写存储；最终窗口位置和尺寸通过现有保存函数显式加入 cleanup。
- Agent 的实际 provider 把已有 `controller.close()` 注册到同一退出服务，随 provider dispose 撤销注册；冷态退出不会为了清理而初始化 Agent。控制器关闭时停止通知、等待已开始的初始化，再并行保存各持有会话、取消订阅并关闭 Pi。
- 启动中的 Pi 使用现有 `starting` 生命周期补记完成 Future；关闭等待它结束，原有“owner 已关闭则关闭新 client”的判断负责归还迟到的子进程。后续发送进入 client 边界时也拒绝已关闭的 owner。
- 原服务中重复的错误处理合并为一个收尾函数，沿用原来的“记录一项失败、继续其他项”行为。cleanup 可带简短名称，在现有日志中记录各项与总耗时；其余后台 provider 只补名称，没有改任务逻辑。
- RAG 仍保留正常检查点与原 60 秒关闭预算；本地超分等任务自身的取消、等待和超时未改。没有新增设置、弹窗、生命周期管理器或统一强杀期限。

业务逻辑集中于退出服务、`main.dart` 和两个 Agent provider/controller 文件；其余九个 Dart 文件只标注 cleanup 名称及整理格式，`resource_window.cpp` 只同步普通关闭的注释。未修改页面、组件或视觉样式。
