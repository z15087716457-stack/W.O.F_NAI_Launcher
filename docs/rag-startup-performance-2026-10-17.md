## 已复现的重复工作

### 共享池退出时重复全量保存，优先处理

`Engine.close()` 无条件保存整个共享池。四类来源包含五个实际 Engine（图库画面与参数各一个）；Worker 依次关闭这些 Engine，最后 `VectorPool.close()` 再保存一次。隔离执行真实 `Worker.run()` 的退出清理，即使索引完全没变，也观测到 **6 次完整检查点保存**。正在建库的生成器退出还可能增加恢复／保存工作，未纳入这个最小复现的 6 次。

按当前 ANN 文件大小，6 次相当于约 **14.2 GB 的重复索引序列化**；这不是实测物理磁盘写入量，系统缓存与文件系统会影响实际 I/O。

同时，Dart `RagClient._close()` 只等待 3 秒便终止宿主，而 Python 给执行线程的退出等待为 15 秒。全量保存若超出 3 秒，就有被打断的风险；若数据库包含尚未保存到 ANN 的向量，下次会再次触发全池恢复。这个退出预算与工作量的矛盾已经由代码确认，但**没有证据表明这次恢复就是由该路径造成**；此前旧触发器导致的检查点过期仍是已确认的另一原因。

建议由池拥有者统一保存一次，并按实际向量变化判断是否需要写；退出握手、取消和最长等待应与真实保存工作匹配。不能只增大超时，也不能为省事忽略不一致检查点。

### 启动重复统计来源状态，随后心跳继续扫描

Worker configure 在返回前已对全部来源调用 status；Dart 首轮 `refresh()` 等待连接后，又立即请求一次 status。隔离四来源完整流程实测 **5 + 5 次分区容量 SUM 查询**，两次来源结果相同。

每次 `Engine.status()` 都执行 `SUM(length(vector)+length(text)+length(name))`，没有容量缓存。查询计划按 collection 索引定位后访问该分区数据行；这是逐行聚合，不是读取一个已有计数。30 秒心跳也会重复这些聚合。Wiki 正文数量／分块估算与图库目录记录首次读取另有自己的工作量，之后一部分受来源签名缓存保护。

建议首轮直接复用 configure 返回值，容量统计按分区实际变化缓存或增量维护；状态心跳只读轻量摘要。此次没有对生产库运行这些 SUM，因此没有把实际启动的分钟数分配给统计阶段。

### 重依赖导入仍有开销，但不能解释恢复阶段的全部等待

Worker ready 前导入推理栈；设置页首次兼容性 probe 也会在另一个进程导入同类依赖。成功 probe 已跨页面保留，不是每次切页都重跑。隔离导入约 6.2 秒；本机完全冷缓存耗时未测，不将它外推为固定启动时间。

可考虑复用当前工作进程的兼容性信息，减少同一会话独立导入。现有主线程预导入用于规避 Windows 原生 DLL 初始化死锁，不能直接删除或挪到执行线程。

## 进一步方案及边界

本地 USearch 支持 `Index.view()` 内存映射。隔离中普通 load 0.016 秒，view 0.0009 秒、首次查询 0.0026 秒，Top-5 与同一已保存索引 load 后一致。但 view 为**不可变索引**，增添和删除分别被拒绝，不能直接替换需要继续建库的现有共享池。若以后采用只读查询模式、写入时转换或分层增量结构，需要另做一致性、Windows 文件替换和峰值内存验证；本轮不推荐直接切换，也未对真实 2.37 GB ANN 做映射实验。

优先级：先统一检查点保存与退出，再去掉重复统计并缓存摘要；进一步评估恢复批次、重复依赖导入。内存映射属于更大改动，放后。所有方向均可保持界面、原图和工具条效果，但还未实施，不能声称已有性能提升。
