## 实现与故障边界

- 有效检查点使用 USearch 2.26.4 的 `view`。沿用一份 `pool-v2` SQLite、一份 ANN、原模型指纹、768 维 f32、cos 度量及全部来源边界；不量化、不拆库、不重嵌入。查询／过滤／融合／重排实现和参数不变。
- 真正增删向量时才用原生 copy 转为可写，保留同一图与检索设置；元数据核对或无变化增量不复制。多个来源交错建库共享可写索引，周期保存不反复映射；全部暂停／结束／挂起后保存并恢复映射。建库期间仍可搜索已提交内容。
- Windows 映射文件不能原地替换。可写切换先取得完整新对象，再释放旧映射；保存发布沿用临时文件与原子替换，退出显式 reset，Python 外部引用仍存活也不继续持有文件句柄。退出不做多余映射，仍由共享池拥有者统一保存。
- 原生 copy 失败保留旧映射；启动映射失败先回落旧 load 读取同一有效图，避免仅因映射失败重建；发布后映射失败保留可写对象供检索及后续重试。取消／发布失败不提前标记检查点干净；损坏／过期索引继续按原规则从已存向量恢复。后台任务结束时的保存异常只报告任务错误，不使执行线程逃逸。

## 测法与结果

机器 i7-13700KF、约 64 GiB RAM、RTX 4080 16 GiB。依赖使用开发隔离环境，版本见 verification.json。六轮新进程以 load／map／map／load／load／map 交替；60 条取自五类来源的真实已存向量，各做原生 top-160、按来源 top-80 及同序重放。四轮自然语言标签检索以 load／map／map／load 对照，使用实际本地 CUDA 嵌入与重排模型、四个测试查询及一次同句重放；调用真实 Engine.search，来源读取固定到同一副本，避免在线变动。未输出用户原文、提示词或结果正文，仅记录结果／候选／向量／分数摘要。

以下为各模式中位数；内存为对应隔离测试进程，包含其运行库，不代表整个 Studio 或整机总内存。

| 指标 | 原 load | 映射 view |
|---|---:|---:|
| 打开 ANN | 1.840 s | 0.082 s |
| 索引＋五来源重放后私有提交 | 4.51 GiB | 0.28 GiB |
| 索引＋五来源重放后驻留工作集 | 3.11 GiB | 1.33 GiB |
| 含模型的标签检索进程私有提交 | 9.22 GiB | 4.99 GiB |

| 后续完整标签检索 | 187 ms | 202 ms |
| 首条固定向量的纯 ANN 查询 | 1.40 ms | 5.57 ms |

后续完整检索观测范围：load 157–238 ms，view 154–217 ms。GPU 嵌入／重排本身有波动，不把约 15 ms 的整体中位数差全部归因于映射。首次触达新页有代价；同序重放的标签来源检索为 2.22→2.30 ms，Wiki 为 3.89→4.05 ms。

本次含模型场景私有提交减少约 4.23 GiB、驻留减少约 2.73 GiB。文件页仍可能留在可回收的系统缓存，不能当作零 RAM，也不能保证整机用量等额下降。模型首次加载仍约十秒，映射没有消除这部分。

大库映射转可写实测 1.61 s，恢复映射 0.16 s；过渡峰值工作集约 6.02 GiB（无模型的过渡探针），不能把检索态节省外推为建库峰值也降低。复制只在实际写入边界发生，连续建库批次复用。
