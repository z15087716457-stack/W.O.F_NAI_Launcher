## 为什么一直显示已补充

`dictionarySources` 在 `lib/core/database/dictionary_downloader.dart` 固定 Tag 2026-10-01 和 Wiki 2026-06-01 的 URL、修订、SHA-256、大小与日期。`SettingsDictionaryUpdater._view` 只比较当前活动提交的 `sourceHash` 与这个常量；相同即 `tagInstalled/wikiInstalled=true`，界面相应按钮禁用。没有联网发现新版、最近检查时间、可更新或检查失败状态。

这不是永不清除的布尔标记：以后程序登记的源哈希变化，按钮会重新可用。但当前程序持续使用同一快照，所以已补充不能解释为「刚检查过，上游已是最新」。界面的可用日期也来自常量，并非本机联网检查结果。

## 建议的行为与实现范围（未实施）

- 保留当前版本信息，提供持续可点的「检查更新」。检查中显示轻量忙碌状态；成功区分「已是最新」与「发现新版」，保存最近成功检查时间；失败显示可重试，并保留已安装版本。未联网检查不能显示已是最新。
- 首次检查只读取小型版本／文件元数据，按内容版本而非「是否导入过」比较；只有存在新版并点击下载更新后才获取大文件。继续固定下载修订、校验、后台构建、取消与失败保护，更新成功后收起进度区域。
- 推荐把已验证来源的版本清单从代码常量移到可独立更新的小清单，登记数据日期、不可变修订 URL、SHA-256、大小、格式版本与来源。以后发布新数据不必重新安装程序；仍需要有人维护这份清单，目前尚无已接通的远端清单，不能只改按钮文案假装已有联网能力。直接读上游 API 也可发现候选，但需要处理格式变化、Git blob 与 SHA-256 对应，以及 Wiki 换数据集的问题。
- Tag 与 Wiki 分别标记是否有更新，整个数据补充任务继续互斥；检查失败不能把本地安装状态改成未补充，也不自动触发全量下载或 RAG 建库。

## 合并规则必须一起考虑

目前 Tag 会补新名称和别名，已有类别不覆盖，使用次数取新旧最大值；Wiki 使用 `INSERT OR IGNORE`，只补缺失文章，**同名文章即使上游改过正文也不会更新**。仅发现新文件再重复执行，不能称为完整数据更新。

实现时应明确哪些来源字段可刷新，保留既有 e621 标签／类别及个人补充。Wiki 上游正文更新需与个人译文分层，并按内容 hash 判定相关译文／中文简释义是否仍适用；不能把旧译文或旧语义资料直接删除。现有小型合并测试已明确验证「保留旧正文」，因此升级该规则需要同步调整验证，不能视为简单 UI 改动。

现有下载器已具备精确大小／SHA-256 校验、后台导入、独立版本发布、取消／失败保留原库和重启恢复，可继续复用。基础资料更新与 RAG 同步是两种状态：成功更新原始资料不代表对应向量已更新，应给出相应来源的同步提示，沿现有机制处理，不自动清空整个共享池。

这行当前仅涵盖标签主库与英文 Wiki；随包中文语义库、个人结构化补翻和共现数据各自独立。中文资料未来可纳入同一版本清单，但属于额外范围，不应把 Tag／Wiki 更新提示误当成全部资料更新。

本轮未新增或运行功能测试、分析及构建：没有生产改动。前一项词库模型状态接线修复仍待本机更新，桌面继续 r23；本调查未扩展其安装范围。
